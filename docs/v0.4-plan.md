# lab-forge v0.4: план (JEB-1898, этап 1 эпика JEB-1896)

Код не меняется, это только план. За основу взят `main` @ 8417b6c (v0.3). Пути к
результатам бенча даны относительно `bench/results/2026-10-18-v0.3/`. Номера строк
сверены с этим коммитом.

## Коротко

- bare выиграл churn методологией: чистый val, CV-калибровка, тесты, которые ловят
  поломку, `pyproject`. v0.3 этому не учит, а правило 10 даже мешает.
- +26% токенов — это в основном лишние шаги (+56% вызовов) и tune через skill (+60%
  на шаге T), а не длина правил.
- Апгрейда нет: повтор на репо v0.1 уходит в Tune, версия нигде не записана.
- v0.4: ядро ≤ 30 строк с методологией и тестами, профиль в каждом репо, tune одним
  скриптом, `upgrade.py`, бенч с весом на методологию и тесты, мутанты, 3 повтора.

### Откуда +26% токенов

Источник — `runs.tsv`, средние по четырём кейсам (без P0 deploy).

| Шаг | Токены v03 / bare, k | Δ | Вызовы инструментов v03 / bare |
|---|---|---|---|
| P1 (код) | 65.6 / 53.3 | +23% | 26.3 / 18.8 |
| P2 (код) | 60.4 / 49.3 | +22% | 20.5 / 14.0 |
| T (tune) | 41.8 / 26.2 | **+60%** | 10.3 / 4.8 |
| P3 (вопрос) | 45.3 / 40.0 | +13% | 13.0 / 7.3 |

Всего 852k против 676k (`v03-bare.md:22`) и 280 вызовов против 179. Если сложить
дельты по шагам, на четырёх кейсах выходит те же 177k. Отсюда причины:

1. **Tune через skill.** Шаг T дороже всего, хотя задача — дописать одну строку. Его
   запускает `global-agents.md:54-55`: tune идёт через skill `lab-forge`, то есть
   агент читает `SKILL.md` (125 строк), потом `references/tune.md`, потом запускает
   `tune.py`. bare просто дописывает строку.
2. **Процесс на каждом шаге.** Ветка (`global-agents.md:9-11`), чтение `AGENTS.md`,
   модуля и вызывающего кода (`:15`), список файлов (`:16-17`). Ещё
   «skill `self-review` ran on the diff» в «Done means» (`assets/templates/rules.md:30-33`):
   это отдельная загрузка skill и отдельный проход по диффу на каждом кодовом шаге.
3. **Дубли в постоянном контексте.** Таблица skills (`assets/templates/rules.md:42-51`)
   повторяет описания, которые харнесс и так кладёт в системный промпт. В repo-копии
   global-блок для не-Claude харнессов повторяет те же 60 строк.
4. **Погрешность замера.** v0.3 мерили в agent-driven режиме: вызов guard-хука там —
   симулированная shell-команда (`report.md:80-81`). Часть дельты на P1/P2 может
   оказаться артефактом. Нужен headless-замер (раздел 5).

Итог по файлам: раздувают `global-agents.md:12-15` (план для M, повторное чтение
`AGENTS.md`), `:54-55` (tune) и `assets/templates/rules.md:30-33`, `:42-51`. Мешают
методологии `global-agents.md:32` и `:39-40` вместе с `principles.md:72-73`. Порядок
`global-agents.md:3-6` даёт overrides отменить что угодно, даже ядро (раздел 4).

## 3. Апгрейд поверх старых версий

### Что ставили версии (по git)

- **v0.1** (`b54d002`) и **v0.2** (`06dca67`) — только уровень репо. Полный свод
  правил (шаблон `rules.md`, ≤ 100 строк, вместе с «как работать») лежит в репо
  `CLAUDE.md`/`AGENTS.md` без маркеров. Ещё есть указатели (`pointer.md`), skills в
  папке skills репо и `.lab-forge/state.md` с таблицей «Files owned by lab-forge».
  Номера версии нет нигде.
- **v0.3** (`8f402c6`, `39e1f6f`, `537f138`, `8417b6c`) добавляет глобальный слой
  `~/.lab-forge/` (`AGENTS.md`, `overrides.md`, `hooks/guard.py`, `state.md`,
  `decide.json`). В глобальный файл каждого харнесса пишется managed-блок
  `<!-- lab-forge:begin sha=… -->`. Репо-`AGENTS.md` теперь хранит только факты.

### Как пишет `scripts/install_global.py` сейчас

- `:200-201` — `~/.lab-forge/AGENTS.md` перезаписывается целиком. Если пользователь
  его правил, правки пропадут без предупреждения. `overrides.md` сохраняется
  (`:202-203`).
- `:97-110` — блок с `sha`. Заменяется первый найденный, текст вне маркеров не
  трогается. Это правильно, только `sha` никто не сверяет с записанным значением,
  поэтому отличить «пользователь правил блок» от «устарел шаблон» нельзя: `check`
  пишет просто DRIFT (`:228-232`).
- `:126` и `:131` — хуки чистятся по подстроке, повторный запуск дублей не создаёт. Это
  оставляем.
- `:183-186` — `rmtree` старой копии skill. Если копия правилась, правки теряются.
- `:77-82` — в `state.md` нет поля версии.
- `SKILL.md:57-60` — если `.lab-forge/state.md` есть, включается Tune-режим.
  Повторный запуск на репо v0.1 до апгрейда не дойдёт никогда.

### Дизайн v0.4

1. **Версия.** Строка `- Version: 0.4.0` в `~/.lab-forge/state.md` и в
   репо-`.lab-forge/state.md`. Старые установки распознаём по отпечаткам. Нет
   `~/.lab-forge` и нет маркеров в репо → v0.1/v0.2. v0.1 от v0.2 отличаем по тексту
   правил из `git show b54d002:…/rules.md`. Есть `lab-forge:begin` без `Version` → v0.3.
2. **Миграции.** Новый модуль `scripts/upgrade.py` с упорядоченным списком
   `(from, to, fn)`: `0.1→0.2→0.3→0.4`. Каждая миграция — чистая функция
   «файлы → новые файлы» без записи на диск. Запись выполняется одним шагом в конце.
3. **Managed-блоки и правки пользователя.** Всё, чем владеет lab-forge, лежит
   внутри `lab-forge:begin <layer> sha=…`, а `sha` блока хранится ещё и в `state.md`.
   При апгрейде:
   - sha на диске совпадает с записанным → блок заменяем;
   - не совпадает → пользователь правил. Его строки, которых нет в старом шаблоне,
     переносим в `## Overrides` (локальный слой) и показываем это в отчёте. Ничего не
     теряем.
   - в v0.1 маркеров нет. Строки, совпадающие с правилами шаблона v0.1/v0.2, считаем
     нашими и убираем (теперь они в ядре). Факты проекта (команды, пути, инварианты,
     словарь) и чужие строки остаются. Блоки ставим вокруг нашей части.
4. **`--dry-run`** по умолчанию печатает unified diff по каждому файлу и список
   перенесённых в Overrides строк, на диск ничего не пишет. `--apply` пишет, а перед
   этим сохраняет бэкап в `~/.lab-forge/backup/<ts>/` и `.lab-forge/backup/<ts>/`.
5. **Идемпотентность.** Второй `upgrade --dry-run` подряд даёт пустой diff. Ни
   одного дубля блока, хука или skill.
6. **Режим в `SKILL.md`.** Новый режим **Upgrade**: state есть, а версия ниже версии
   движка (или её нет) → сначала `upgrade --dry-run`, показываем diff, применяем,
   потом обычный Tune.

Эталон — установка v0.1 у Yeldos. Фикстуру собираем из шаблонов `b54d002` с
заполненными плейсхолдерами и парой «ручных» строк. Финальная проверка на его
машине — на этапе 3, только в режиме `--dry-run`.

## 4. Слои правил

| Слой | Где лежит | Кто меняет | Что внутри |
|---|---|---|---|
| **Ядро** (C1…Cn) | `~/.lab-forge/core.md`, блок `lab-forge:begin core` | только апгрейд lab-forge | ветка, скоуп, «не врать о результате», методология данных, смысл тестов, `file:line` только после чтения. ≤ 30 строк |
| **Профиль** (P1…Pn) | блок `lab-forge:begin profile` в репо-`AGENTS.md` | deploy и апгрейд | инварианты домена из `references/profiles/*.md`. Ставится и в seed-режиме |
| **Умолчания** (D1…Dn) | `~/.lab-forge/defaults.md` | tune может переопределить | размер плана, язык, число тестов, формат ответа, коммиты |
| **Локально** | репо-`AGENTS.md`/`CLAUDE.md` вне блоков и `## Overrides` | пользователь и агент через tune | факты проекта, предпочтения |

Порядок при конфликте: явная просьба пользователя в этой сессии → ядро и инварианты
профиля → локальные правила и overrides → умолчания. Сейчас (`global-agents.md:3-6`)
overrides стоят выше всех правил. Это меняется: overrides могут заменить или уточнить
D- и P-правила (ссылкой `replaces D3`) и что угодно добавить. Ослабить C-правило они
не могут.

Как агенту разрешено дополнять правила:

- `tune.py add "<line>"` пишет строку в `## Overrides`. Если в строке есть ссылка на
  `C<n>` или она совпадает с отрицанием C-правила по списку ключевых фраз в
  `core.md`, скрипт отказывает: «это ядро; скажи явно в чате, если нужно на одну
  задачу».
- Агент сам дописывает факты в локальный слой (это правило 13 v0.3). Блоки ядра и
  профиля он не трогает: `guard.py hook` блокирует Edit/Write внутри
  `lab-forge:begin core|profile` и запись в `~/.lab-forge/core.md`.
- `install_global.py check` сверяет sha ядра и профиля и сообщает о ручной правке.

## 5. Бенч

**`bench/rubric.md`.** Два новых критерия в каждом кодовом шаге:

- `methodology` — каждый обучаемый шаг (скейлинг, энкодинг, калибровка, порог,
  early stopping, подбор гиперпараметров) учится на строках, на которых его потом не
  оценивают. Нет утечки по времени и группам, сиды и сплит одни для всех моделей.
- `tests` — упадёт ли тест, если сломать поведение, которое он называет. Судья
  обязан сломать одну функцию в копии и прогнать тесты, и написать, что получилось.
  Тесты, которые только повторяют конфиг или вход, — дефект.
- В `review` у кейсов добавить «run bare `pytest`», а не только `python -m pytest`.

**`bench/report.py`.** Вместо «code sum of 30» (`report.py:126`, `:200`) — взвешенная
сумма: methodology ×2, tests ×2, correctness ×1.5, success ×1, scope ×1,
practices ×1, optimality ×0.5, bloat ×0.5. Победителя считаем по большинству повторов,
у каждой метрики — разброс между повторами. Новые строки: «tokens per solved task vs
bare, %», «tool calls per solved task», «mutants caught», «bare pytest green».

**`bench/bench.py`.**

- Мутанты: `[[mutants]]` в `case.toml` — патч, который ломает поведение (у churn:
  калибратор на val, порог 0.5, утечка test в fit). Скрипт накладывает патч на снапшот
  агента и запускает его тесты. Метрика — доля мутантов, которые тесты поймали. Это
  объективная часть критерия «смысл тестов», без судьи.
- Повторы: значение `--reps` по умолчанию уже 2 (`bench.py:618`), а v0.3 гоняли с 1.
  Для итогового A/B ставим `--reps 3`.
- Токены: `claude()` складывает все четыре поля usage (`bench.py:562-565`). Пишем их в
  `runs.tsv` по отдельности (input, output, cache read, cache write), чтобы видеть,
  где растёт.
- Итоговый замер — только headless (`bench.py all`), тогда в агентском режиме не будет
  симулированных хуков.
- Судья из другой семьи: флаг `--judge-cmd` с адаптерами `codex exec` (OpenAI) и
  `gemini -p`. Пока платного доступа нет, работает бесплатная замена: судья Claude
  дважды, с переставленными X/Y, расхождение пишется как «position bias». **Платный
  ключ OpenAI или Gemini для судьи — решение Yeldos.**
