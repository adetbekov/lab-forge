# lab-forge v0.4: plan (JEB-1898, stage 1 of epic JEB-1896)

Plan only, no code changes. Base: `main` @ 8417b6c (v0.3). Bench paths are relative to
`bench/results/2026-10-18-v0.3/`; line numbers match that commit.

## In short

- bare won churn on methodology: a clean validation split, CV calibration, tests that
  catch breakage, a `pyproject`. v0.3 teaches none of that, and rule 10 works against it.
- The +26% tokens come mostly from extra steps (+56% tool calls) and tune via the skill
  (+60% on step T), not from rule length.
- There is no upgrade path: rerunning on a v0.1 repo lands in Tune mode, and no version
  is recorded anywhere.
- v0.4: a core of ≤ 30 lines with methodology and test rules, the profile in every repo,
  tune as one script call, `upgrade.py`, and bench criteria for methodology and tests,
  added on top of the existing bench without changing past results.

## 1. External techniques: what we take

| Set | Instruction following | Short docs and tokens | We take |
|---|---|---|---|
| [Anthropic Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills), [anthropics/skills](https://github.com/anthropics/skills) | Only a skill's name and description sit in context; the body loads on trigger | Scripts are run, not read; detail lives in separate files | A small core. Tune runs a script without reading `SKILL.md` |
| [Claude Code best practices](https://www.anthropic.com/engineering/claude-code-best-practices) | Tune CLAUDE.md like a prompt and check each rule is obeyed; "IMPORTANT" for critical rules | Short CLAUDE.md, test first, then code | Every core rule has a bench case that checks it; a rule with no case is cut |
| [HumanLayer: Writing a good CLAUDE.md](https://www.humanlayer.dev/blog/writing-a-good-claude-md) | Models reliably follow ~150-200 instructions, and the system prompt already uses ~50. The harness marks the file "may or may not be relevant", so non-universal lines get skipped | Root file < 60 lines. A linter enforces style, not an instruction. `file:line` pointers instead of copied code | An always-loaded budget of ≤ 60 lines for core plus repo. Style rules that ruff catches go away |
| [Karpathy guidelines](https://github.com/forrestchang/andrej-karpathy-skills) | Four principles in ~70 lines. Every changed line traces back to the request | "Goal-driven execution": turn the task into a test that fails, then passes | "A test must fail when the behaviour it names breaks" goes into the core |
| [obra/superpowers](https://github.com/obra/superpowers) | The test-driven-development skill: RED, GREEN, REFACTOR; the test must fail before the code exists | A heavy process: many steps, many tokens | Only the RED idea, as bench mutants. Not the workflow |
| [AGENTS.md](https://agents.md) | One open format. In a monorepo the nearest file wins; an explicit user ask wins over it | No separate file per harness | The local layer is the nearest `AGENTS.md`. Core and profile go into it as managed blocks |
| [Cursor rules](https://cursor.com/docs/context/rules) | Rules are always on, glob-scoped, agent-requested or manual | Specific rules load only next to matching files | Profile rules stay short and concrete; the rest is a link |
| [ponytail](https://github.com/DietrichGebert/ponytail) (already benched), [caveman](https://github.com/JuliusBrussee/caveman) | ponytail: the ladder skip, reuse, stdlib, … | ponytail is the cheapest arm, 620k (`all-arms.md:10`), but has weaker practices, 3.9 (`all-arms.md:37`). caveman compresses output only, ~65% by its own numbers | The ladder is already in v0.3. Not caveman: our metric is dominated by input and context, not replies; the token breakdown in section 5 will confirm it |

The common thread: the successful sets are short, hand mechanical checks to hooks and
linters, and delete a rule that does not change measured behaviour. v0.3 is the
opposite on both counts: plenty of process (plans, reading callers, skills) and no
concrete rules about ML methodology or tests.

### Where the +26% tokens come from

Source: `runs.tsv`, means over the four cases (P0 deploy excluded).

| Step | Tokens v03 / bare, k | Δ | Tool calls v03 / bare |
|---|---|---|---|
| P1 (code) | 65.6 / 53.3 | +23% | 26.3 / 18.8 |
| P2 (code) | 60.4 / 49.3 | +22% | 20.5 / 14.0 |
| T (tune) | 41.8 / 26.2 | **+60%** | 10.3 / 4.8 |
| P3 (question) | 45.3 / 40.0 | +13% | 13.0 / 7.3 |

Totals are 852k vs 676k (`v03-bare.md:22`) and 280 tool calls vs 179. The per-step
deltas over four cases add up to the same 177k. The causes:

1. **Tune via the skill.** Step T is the most expensive one, though the task is one
   appended line. `global-agents.md:54-55` routes tune through skill `lab-forge`: the
   agent reads `SKILL.md` (125 lines), then `references/tune.md`, then runs `tune.py`.
   bare just appends the line.
2. **Process on every step.** A branch (`global-agents.md:9-11`), reading `AGENTS.md`,
   the module and its callers (`:15`), listing files (`:16-17`). Plus "skill
   `self-review` ran on the diff" in Done means (`assets/templates/rules.md:30-33`): one
   more skill load and one more pass over the diff on every coding step.
3. **Duplicates in the always-loaded context.** The skills table
   (`assets/templates/rules.md:42-51`) repeats descriptions the harness already puts in
   the system prompt. The repo copy for non-Claude harnesses repeats the same 60 lines.
4. **Measurement noise.** v0.3 ran agent-driven, where each guard-hook call is a
   simulated shell command (`report.md:80-81`). Part of the P1/P2 delta may be an
   artifact; a headless run settles it (section 5).

By file: bloat comes from `global-agents.md:12-15` (plan for M, rereading `AGENTS.md`),
`:54-55` (tune) and `assets/templates/rules.md:30-33`, `:42-51`. Methodology suffers from
`global-agents.md:32` and `:39-40` together with `principles.md:72-73`. The precedence in
`global-agents.md:3-6` lets overrides cancel anything, the core included (section 4).

## 3. Upgrading over older versions

### What each version installed (from git)

- **v0.1** (`b54d002`) and **v0.2** (`06dca67`): repo level only. The full rule set
  (template `rules.md`, ≤ 100 lines, including how to work) sits in the repo
  `CLAUDE.md`/`AGENTS.md` with no markers, plus pointers (`pointer.md`), skills in the
  repo skills folder and `.lab-forge/state.md` with a "Files owned by lab-forge" table.
  No version anywhere.
- **v0.3** (`8f402c6`, `39e1f6f`, `537f138`, `8417b6c`) adds the global layer
  `~/.lab-forge/` (`AGENTS.md`, `overrides.md`, `hooks/guard.py`, `state.md`,
  `decide.json`) and a managed block `<!-- lab-forge:begin sha=… -->` in each harness's
  global file. The repo `AGENTS.md` now holds facts only.

### How `scripts/install_global.py` writes today

- `:200-201`: `~/.lab-forge/AGENTS.md` is overwritten whole, so user edits vanish
  silently. `overrides.md` is kept (`:202-203`).
- `:97-110`: a block with `sha`; the first one found is replaced, text outside the
  markers is untouched. That is right, but the `sha` is never compared to a recorded
  value, so "the user edited the block" and "the template is newer" look the same:
  `check` just prints DRIFT (`:228-232`).
- `:126`, `:131`: hooks are cleaned by substring, so reruns add no duplicates. Keep it.
- `:183-186`: `rmtree` of the old skill copy; edits to the copy are lost.
- `:77-82`: `state.md` has no version field.
- `SKILL.md:57-60`: when `.lab-forge/state.md` exists, Tune mode starts, so a rerun on a
  v0.1 repo never reaches an upgrade.

### v0.4 design

1. **Version.** A `- Version: 0.4.0` line in `~/.lab-forge/state.md` and in the repo
   `.lab-forge/state.md`. Older installs are fingerprinted: no `~/.lab-forge` and no
   markers in the repo means v0.1/v0.2, told apart by the rule text from
   `git show b54d002:…/rules.md`; `lab-forge:begin` without `Version` means v0.3.
2. **Migrations.** A new `scripts/upgrade.py` with an ordered list of `(from, to, fn)`:
   `0.1→0.2→0.3→0.4`. Each migration is a pure function from files to files; one write
   step at the end.
3. **Managed blocks and user edits.** Everything lab-forge owns sits inside
   `lab-forge:begin <layer> sha=…`, and each block's `sha` is also stored in `state.md`.
   On upgrade:
   - the sha on disk matches the stored one: replace the block;
   - it does not: the user edited it. Their lines that are not in the old template move
     to `## Overrides` (the local layer), and the report lists them. Nothing is lost.
   - v0.1 has no markers. Lines that match v0.1/v0.2 template rules are ours and go away
     (they now live in the core). Project facts (commands, paths, invariants, words) and
     foreign lines stay; blocks are placed around our part.
4. **`--dry-run`** is the default: a unified diff per file plus the lines moved to
   Overrides, nothing written. `--apply` writes after a backup to
   `~/.lab-forge/backup/<ts>/` and `.lab-forge/backup/<ts>/`.
5. **Idempotence.** A second `upgrade --dry-run` in a row prints an empty diff. No
   duplicate block, hook or skill.
6. **Mode in `SKILL.md`.** A new **Upgrade** mode: state exists and its version is older
   than the engine (or missing), so run `upgrade --dry-run`, show the diff, apply, then
   continue with Tune.

The reference case is Yeldos's v0.1 install. The fixture is built from the `b54d002`
templates with filled placeholders and a couple of hand-written lines. The final check on
his machine is in stage 3, `--dry-run` first.

## 4. Rule layers

| Layer | Where | Who changes it | Contents |
|---|---|---|---|
| **Core** (C1…Cn) | `~/.lab-forge/core.md`, block `lab-forge:begin core` | lab-forge upgrade only | branch, scope, no false claims, data methodology, meaningful tests, `file:line` only after reading. ≤ 30 lines |
| **Profile** (P1…Pn) | block `lab-forge:begin profile` in the repo `AGENTS.md` | deploy and upgrade | domain invariants from `references/profiles/*.md`. Installed in seed mode too |
| **Defaults** (D1…Dn) | `~/.lab-forge/defaults.md` | tune may override | plan size, language, test count, reply format, commits |
| **Local** | repo `AGENTS.md`/`CLAUDE.md` outside blocks, `## Overrides` | user, and the agent through tune | project facts, preferences |

On conflict: the user's explicit ask in this session, then core and profile invariants,
then local rules and overrides, then defaults. Today (`global-agents.md:3-6`) overrides
beat every rule. In v0.4 overrides may replace or refine D and P rules (by reference,
`replaces D3`) and add anything, but cannot weaken a C rule.

How the agent may extend the rules:

- `tune.py add "<line>"` writes the line to `## Overrides`. If it references `C<n>` or
  matches the negation of a C rule by the key phrases listed in `core.md`, the script
  refuses: "this is core; ask explicitly in chat if you need it for one task".
- The agent adds facts to the local layer on its own (v0.3 rule 13). It never edits core
  or profile blocks: `guard.py hook` blocks Edit/Write inside
  `lab-forge:begin core|profile` and writes to `~/.lab-forge/core.md`.
- `install_global.py check` compares the core and profile sha and reports a hand edit.

## 5. Bench

**Rule: past results stay as they are; v0.4 only adds.** Everything under
`bench/results/` is never rewritten or regenerated, and every existing metric keeps its
definition, so new numbers stay comparable with old ones:

- `bench/rubric.md`: the six code criteria, the question criteria, `clarity` and
  `questions` keep their exact wording and 1-5 scale. New criteria are appended after
  them.
- `bench/report.py`: "code sum of 30" (`report.py:126`, `:200`) stays computed as today.
  The weighted score is an extra row next to it.
- `runs.tsv`: new columns go at the end only. `report.py` still reads the old files.
- `bench/cases/*/case.toml`: prompts, checks, seed 1877 and fixtures stay unchanged.
  Mutants go into a new `[[mutants]]` section.
- Every run records its mode (`headless` or `agent`), and the report never mixes the two
  in one table.

What we add:

- **Rubric criteria** for every coding step. `methodology`: each fitted step (scaling,
  encoding, calibration, threshold, early stopping, hyperparameter search) learns on rows
  it is not evaluated on; no leakage by time or group; the same seed and split for all
  models. `tests`: would a test fail if the behaviour it names broke? The judge breaks
  one function in a copy, reruns the tests and reports the outcome; a test that only
  echoes config or input is a defect. The case `review` text gains "also run bare
  `pytest`".
- **Weighted score** (new row): methodology ×2, tests ×2, correctness ×1.5, success ×1,
  scope ×1, practices ×1, optimality ×0.5, bloat ×0.5. The winner is the majority over
  repeats, with the spread between repeats for each metric. New rows: tokens per solved
  task vs bare in %, tool calls per solved task, mutants caught, bare `pytest` green.
- **Mutants** (`bench/bench.py`): a patch that breaks behaviour (churn: calibrator on
  validation, threshold fixed at 0.5, test rows in fit) is applied to the agent's
  snapshot and its tests are run. The metric is the share of mutants caught: the
  objective half of "meaningful tests", with no judge.
- **Repeats**: `--reps` already defaults to 2 (`bench.py:618`), but v0.3 ran 1. The final
  A/B uses `--reps 3`.
- **Token breakdown**: `claude()` sums all four usage fields (`bench.py:562-565`). The sum
  stays as the existing column; input, output, cache read and cache write are added as
  separate columns.
- **Headless**: the final measurement uses `bench.py all`, with no simulated hooks.
- **Cross-family judge**: a `--judge-cmd` flag with adapters for `codex exec` (OpenAI) and
  `gemini -p`. The free fallback until then is the Claude judge run twice with X/Y
  swapped, with the disagreement reported as position bias. **A paid OpenAI or Gemini key
  for the judge is Yeldos's call.**

## Risks

- If v0.1 is not recognized by its text, nothing is removed: blocks go next to it and
  the diff is shown.
- Until there is a cross-family judge, quality scores are a guide. Mutants and bare
  `pytest` do not depend on the judge.
- The token target rests on an agent-driven measurement. If headless shows less than
  +26%, the cuts can be smaller.
