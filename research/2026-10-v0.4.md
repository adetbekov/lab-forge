[`docs/v0.4-plan.md`](../docs/v0.4-plan.md) (PR #12, на английском — PR #13, JEB-1898), и здесь он не

Список задач в разделе 6 заменяет раздел 7 плана.

Звёзды и даты последнего push взяты из `gh api repos/...` 2026-10-19. Документацию
я открывал сам, ничего не пересказано по памяти. Сырые данные бенча лежат в рабочей
копии JEB-1895 (`pt/ws`, `pt/logs`, `pt/runs-v03-bare.tsv`). Строки `file:line`
ниже ссылаются на эти рабочие копии.

## Коротко

- **+26% — это поштучный счёт токенов, а не деньги.** `bench.py:562-565` просто
  складывает `input + output + cache_read + cache_creation`. Каждый вызов
  инструмента заново читает весь контекст из кэша. На Opus 5.5 это чтение стоит
  0.05× цены входа, но в нашем счёте идёт как 1×. Токены почти линейно растут с
  числом вызовов (r = 0.92 на 72 сессиях), а у v0.3 их на 56% больше. Метрику надо
  чинить до того, как оптимизировать.
- **Основная экономия даст не сжатие правил, а меньше лишних шагов.** Это tune
  через skill, повторное чтение `AGENTS.md` и `state.md`, и self-review на каждом
  шаге. Сжатый ввод, судя по статье CAVEWOMAN, увеличивает итоговую стоимость.
  Сжимать стоит только ответы.
- **Порядок приоритетов в прозе не работает.** Claude Code прямо пишет, что при
  конфликте пользовательских и проектных правил модель может выбрать любое.
  Неизменяемое ядро держится на хуках и проверках скриптом, а не на фразе
  «ядро важнее».
- **Для апгрейда лучше подходит схема copier**: эталон того, что было установлено,
  плюс 3-way merge. Построчного сравнения с шаблоном мало. Для блоков v0.3 эталон
  восстанавливается точно, для v0.1 нужна миграция по отпечаткам.
- **Указатель v0.1 стоит токенов.** Строка «Read AGENTS.md before any action»
  заставляет агента читать файл инструментом в каждой сессии. `@AGENTS.md` делает
  то же самое бесплатно.

## 2. Техники экономии токенов

Эффект оценён по нашим данным: регрессия «токены ≈ a + b × вызовы» по
`runs-v03-bare.tsv` даёт для v0.3 a = 30.1k, b = 1.32k, для bare a = 22.1k,
b = 1.80k. Замер везде делается в headless: `claude -p --output-format json`, поля
`usage` плюс `total_cost_usd` и `num_turns`.

| # | Техника | Что делаем в lab-forge | Ожидаемый эффект | Как замерить |
|---|---|---|---|---|
| 1 | **Честная метрика с учётом кэша** | В `runs.tsv` пишем 4 поля usage по отдельности, `cost_usd` и «взвешенные токены» = input + 1.25 × cache_write + 0.1 × cache_read + output | Сама по себе ничего не экономит. Но разница с bare, скорее всего, сильно меньше 26%: лишние вызовы v0.3 почти целиком идут через чтение из кэша | Сравнить `cost_usd` v0.3 и bare на тех же 16 сессиях. Цель JEB-1896 ставим на `cost_usd` и взвешенные токены за решённую задачу |
| 2 | **Дешёвый tune**: прямой вызов `tune.py add` по правилу 18 вместо чтения `SKILL.md` и `tune.md` (около 11 KB) | Правило 18 из одной строки и маленький skill `lab-forge-tune` (≤ 30 строк) на случай без скрипта | Шаг T: 41.8k → ~28k (около −13k на T, −52k на 4 кейсах, ~30% всего перерасхода) | Токены шага T у v0.4 против bare, цель ≤ bare +10% |

## 3. v0.3 против bare: какие правила поправить

Разбор по кейсам есть в `docs/v0.4-plan.md` раздел 2. Здесь новые факты и итоговые
правки.

Новые факты:

- **Повтор v04 на churn (`churn-faf35a`) провалился по той же схеме.** Правило
  «each fitted step gets its own split or CV fold» было в профиле
  (`skills/v04/.../classic-ml.md:32-34`), но генератор сжал его до «nothing is chosen
  on the test split» (`ws/churn-faf35a/AGENTS.md:31-32`). Калибровка и порог снова
  сделаны на одном X_val (`churn/train.py:92-95`), а агент объяснил это так: «with
  sigmoid… harmless». Вывод: правило методологии должно жить в ядре или
  копироваться дословно, без пересказа генератором.
- **Голый `pytest` красный в обоих новых проектах v0.3** (churn и rparse). У bare в
  обоих есть `pyproject.toml` с `pythonpath`. Причина в `generation.md:66-68`
  («prescribe no package layout»): агент относит `pyproject` к layout.
- **Тесты v0.3 не ловят поломку.** Тест конфига в churn проверяет, что конфиг
  повторён в `metrics` (`tests/test_train.py:46-57`), а не что модель его
  использует. У bare тест проверяет, что модель изменилась (`:63-69`), а порог
  проверен на кейсе, посчитанном вручную (`:56-60`).
- **v0.3 прав, где bare раздувает.** 225 строк тестов на 10 строк кода в optuna,
  матрица 14×2 в encoders, CHANGELOG вне задачи, CLI-флаги и Brier score, которых
  никто не просил.

Правки (5, все в формулировке для шаблона):

1. **`global-agents.md`, правило 10 → ядро.** «Test the acceptance criteria through
   real interfaces. Each test must fail when the behaviour it names breaks: assert
   the effect, never an echo of the input or config. A helper you write (split,
   threshold, metric) gets one hand-computed case. No edge-case matrices unless asked.»
2. **`global-agents.md`, новое правило ядра.** «Sound method is part of "complete";
   rule 8 never trims it. Every fitted step (preprocessing, calibration, threshold,
   tuning, early stopping) uses rows no earlier step was fitted on, or CV inside the
   training rows. If the ask allows a weaker method, do the sound one and say so in
   one line.»
3. **`references/generation.md:66-68` и seed в `SKILL.md`.** «A new Python project
   gets a minimal `pyproject.toml` (name, deps, `[tool.pytest.ini_options]`
   `pythonpath = ["."]`). It is setup, not layout. The phase 6 dry run includes a bare
   `pytest`.»
4. **`references/profiles/*.md` и `generation.md`.** Инварианты профиля копируются в
   репо-`AGENTS.md` дословно, в блоке `lab-forge:begin profile`. `verify_setup.py`
   проверяет, что их sha совпадает с профилем.
5. **`global-agents.md`, правило про доки → ядро.** «README: what it is and how to
   run it. Docstring: the contract and why, 1-2 lines. Comment: only a non-obvious
   why. No "This module provides", no bold, no emoji, no summary of what you just
   did.» Плюс 6 примет из Wikipedia в `skill-self-review.md`.

Из bare не берём: коммиты в `main` (8/8), правки вне задачи, флаги и метрики,
которых не просили, путь к конфигу от cwd, `print` вместо логгера, объём тестов.

## 4. Апгрейд и слои: поправки к плану

План (раздел 3–4 `docs/v0.4-plan.md`) верный по сути: версия, миграции,
`--dry-run`, бэкап, слои core / profile / defaults / local. Уточняю три места.

**Слияние правок пользователя.** В плане строки пользователя, которых нет в старом
шаблоне, переносятся в `## Overrides`. Это теряет контекст: правка внутри правила
превращается в отдельную строку-дубль. Лучше по схеме copier:

1. При каждой установке рендер блока сохраняется в `~/.lab-forge/base/<file>.md`.
2. При апгрейде, если sha блока на диске совпадает с sha в маркере, блок просто
   заменяется.
3. Иначе выполняется `git merge-file <на диске> <base> <новый рендер>`. Без
   конфликтов результат пишется; при конфликте рядом кладётся `.rej`, файл не
   меняется, а `--dry-run` показывает оба варианта.
4. Для блоков v0.3 base восстанавливается точно: шаблон из
   `git show 8417b6c:.../global-agents.md` и canary из `state.md`. Миграция кладёт эти
   шаблоны в `scripts/migrations/`, чтобы git-история не была нужна.
5. Для v0.1/v0.2 base нет: файлы писал агент по шаблону, не рендер. Здесь годится
   метод из плана, но по секциям, а не по строкам:
   - секции с заголовками шаблона v0.1 («Size the task first», «How code is written
     here», «Check before saying "done"», «Delivery») заменяются ядром;
   - «Read first», «Invariants», «Languages», пункт `{{pain_point_rule}}` и всё
     нераспознанное остаются фактами вне блока;
   - текстовый указатель меняется на `@AGENTS.md`.

**Распознавание версии.** Отпечатки по фактическим файлам:

| Версия | Признак |
|---|---|
| v0.1 | репо `.lab-forge/state.md` без строки `- Mode:`, заголовок правил `# Rules for AI agents -`, нет `~/.lab-forge/` |
| v0.2 | то же, но в `state.md` есть `- Mode:` |
| v0.3 | `~/.lab-forge/state.md` с `- Canary:`, маркер `lab-forge:begin sha=` без `v=` |
