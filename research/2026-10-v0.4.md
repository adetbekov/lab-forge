# lab-forge v0.4: what others do, where the tokens go, plan (JEB-1897)

This is the research for epic JEB-1896. The internal review of v0.3 is already in
[`docs/v0.4-plan.md`](../docs/v0.4-plan.md) (PR #12, in English in PR #13, JEB-1898), and it is
not repeated here. This report adds three things to it: external sources with checked
links, token-saving techniques with a way to measure each, and corrections to the plan.
The task list in section 6 replaces section 7 of the plan.

Stars and last push dates come from `gh api repos/...` on 2026-10-19. I opened the
documentation myself; nothing is retold from memory. Raw bench data lives in the JEB-1895
working copy (`pt/ws`, `pt/logs`, `pt/runs-v03-bare.tsv`). The `file:line` references
below point into those working copies.

## Summary

- **+26% is a raw token count, not money.** `bench.py:562-565` just adds up
  `input + output + cache_read + cache_creation`. Every tool call reads the whole
  context from the cache again. On Opus 5.5 that read costs 0.05× the input price, but
  our count treats it as 1×. Tokens grow almost linearly with the number of calls
  (r = 0.92 over 72 sessions), and v0.3 makes 56% more of them. The metric has to be
  fixed before we optimise against it.
- **The main saving comes from fewer extra steps, not from compressing the rules.** That
  means tune through the skill, re-reading `AGENTS.md` and `state.md`, and self-review on
  every step. Compressed input, according to the CAVEWOMAN paper, raises the total cost.
  Only replies are worth compressing.
- **A priority order written in prose does not work.** Claude Code states plainly that
  when user and project rules conflict, the model may pick either. An immutable core is
  held by hooks and script checks, not by the sentence "the core wins".
- **For upgrades the copier scheme fits better**: a reference copy of what was installed
  plus a 3-way merge. A line-by-line comparison with the template is not enough. For v0.3
  blocks the reference can be rebuilt exactly; v0.1 needs a migration by fingerprints.
- **The v0.1 pointer costs tokens.** The line "Read AGENTS.md before any action" makes
  the agent read the file with a tool in every session. `@AGENTS.md` does the same for
  free.

## 2. Token-saving techniques

The effect is estimated from our data: the regression "tokens ≈ a + b × calls" on
`runs-v03-bare.tsv` gives a = 30.1k, b = 1.32k for v0.3 and a = 22.1k, b = 1.80k for
bare. Every measurement is done headless: `claude -p --output-format json`, the `usage`
fields plus `total_cost_usd` and `num_turns`.

| # | Technique | What we do in lab-forge | Expected effect | How to measure |
|---|---|---|---|---|
| 1 | **An honest metric that accounts for the cache** | `runs.tsv` gets the 4 usage fields separately, `cost_usd` and "weighted tokens" = input + 1.25 × cache_write + 0.1 × cache_read + output | Saves nothing by itself. But the gap to bare is most likely far below 26%: v0.3's extra calls go almost entirely through cache reads | Compare `cost_usd` of v0.3 and bare on the same 16 sessions. The JEB-1896 target is set on `cost_usd` and weighted tokens per solved task |
| 2 | **Cheap tune**: a direct `tune.py add` call through rule 18 instead of reading `SKILL.md` and `tune.md` (about 11 KB) | Rule 18 as one line and a small skill `lab-forge-tune` (≤ 30 lines) for the case without the script | Step T: 41.8k → ~28k (about −13k per T, −52k over 4 cases, ~30% of the whole overspend) | Step T tokens of v0.4 against bare, target ≤ bare +10% |
| 3 | **Do not re-read what is already loaded** | Into the core: "Rules and repo `AGENTS.md` are already in context; do not open them. Read `.lab-forge/state.md` only in tune or upgrade". v0.1 pointers → `@AGENTS.md` | Minus 1–2 calls per session: ≈ −2…−3k per step; on P3 the gap shrinks from +5.3k to ~+2k | `num_turns` and tokens on P3 (the floor of a session's cost). Grep session logs for `Read .*AGENTS.md` |
| 4 | **Self-review only for M and larger**, with the 5 main checks written straight into rule 17 | Remove "skill `self-review` ran" from "Done means" (`rules.md:30-33`) | −3…−5k per code step S | Tokens on P1/P2, the share of steps where the skill was loaded (visible in the tool log) |
| 5 | **A stable prefix for the cache** | Blocks without dates or counters, a fixed file order. Bookkeeping goes into `<!-- -->`, which Claude strips | A repeated session reads the prefix at 0.05–0.1×. Breaking the cache is expensive: a write costs 1.25× | `cache_creation_input_tokens` does not grow on the second session in a row. Cache share = cache_read / all input |
| 6 | **Compressed replies, plain rule text** | Refine rule 15: "≤ 120 words for a code step unless asked". Do not compress the rule text | According to CAVEWOMAN, compressed output is 1.4–2.4× cheaper, compressed input is about 1.15× more expensive and less accurate. Our replies are 270–660 words, ~5–10% of tokens | `output_tokens` and `reply_words` (already in `runs.tsv`), plus quality by the rubric |
| 7 | **Grep first, read files by range** | Into the core: "Locate with grep or symbols first; read the lines you need". The code map from `bench/memory/codemap.py` only on request | Fewer full reads on optuna and encoders (70k and 8k lines). Estimate: −5…−10% on P1/P2 of large repos | Tokens and `num_turns` on the optuna and encoders cases separately |
| 8 | **Hooks stay silent until they block** | `guard.py hook` prints nothing on success. The agent-driven bench does not simulate the hook on every call | ≈ 0 tokens headless. Agent-driven, it removes an artifact: every hook call was a separate shell command | Compare `num_turns` of the same session headless and agent-driven |
| 9 | **Hand noisy work to a subagent** (test runs, logs) | Only as advice in the profile, not a rule: in total it can cost more | A smaller main context, the money outcome is unclear | The per-model usage breakdown in the JSON, `total_cost_usd` |

Items 1–5 go into v0.4. Items 6–7 are done if the stage 3 A/B shows no loss of quality.
Item 9 is only recorded.

## 3. v0.3 against bare: which rules to fix

The case-by-case review is in `docs/v0.4-plan.md` section 2. Here are the new facts and
the resulting fixes.

New facts:

- **The v04 rerun on churn (`churn-faf35a`) failed the same way.** The rule "each fitted
  step gets its own split or CV fold" was in the profile
  (`skills/v04/.../classic-ml.md:32-34`), but the generator squeezed it into "nothing is
  chosen on the test split" (`ws/churn-faf35a/AGENTS.md:31-32`). Calibration and the
  threshold were again fitted on the same X_val (`churn/train.py:92-95`), and the agent
  explained it with "with sigmoid… harmless". Conclusion: the methodology rule has to
  live in the core or be copied verbatim, without the generator retelling it.
- **Bare `pytest` is red in both new v0.3 projects** (churn and rparse). Bare has a
  `pyproject.toml` with `pythonpath` in both. The cause is `generation.md:66-68`
  ("prescribe no package layout"): the agent counts `pyproject` as layout.
- **v0.3 tests do not catch a breakage.** The config test in churn checks that the
  config is repeated in `metrics` (`tests/test_train.py:46-57`), not that the model uses
  it. In bare the test checks that the model changed (`:63-69`), and the threshold is
  checked against a hand-computed case (`:56-60`).
- **v0.3 is right where bare bloats.** 225 lines of tests for 10 lines of code in optuna,
  a 14×2 matrix in encoders, a CHANGELOG outside the task, CLI flags and a Brier score
  nobody asked for.

Fixes (5, all worded for the template):

1. **`global-agents.md`, rule 10 → core.** "Test the acceptance criteria through
   real interfaces. Each test must fail when the behaviour it names breaks: assert
   the effect, never an echo of the input or config. A helper you write (split,
   threshold, metric) gets one hand-computed case. No edge-case matrices unless asked."
2. **`global-agents.md`, a new core rule.** "Sound method is part of "complete";
   rule 8 never trims it. Every fitted step (preprocessing, calibration, threshold,
   tuning, early stopping) uses rows no earlier step was fitted on, or CV inside the
   training rows. If the ask allows a weaker method, do the sound one and say so in
   one line."
3. **`references/generation.md:66-68` and seed in `SKILL.md`.** "A new Python project
   gets a minimal `pyproject.toml` (name, deps, `[tool.pytest.ini_options]`
   `pythonpath = ["."]`). It is setup, not layout. The phase 6 dry run includes a bare
   `pytest`."
4. **`references/profiles/*.md` and `generation.md`.** Profile invariants are copied into
   the repo `AGENTS.md` verbatim, in a `lab-forge:begin profile` block. `verify_setup.py`
   checks that their sha matches the profile.
5. **`global-agents.md`, the docs rule → core.** "README: what it is and how to
   run it. Docstring: the contract and why, 1-2 lines. Comment: only a non-obvious
   why. No "This module provides", no bold, no emoji, no summary of what you just
   did." Plus 6 signs from Wikipedia in `skill-self-review.md`.

What we do not take from bare: commits to `main` (8/8), edits outside the task, flags
and metrics nobody asked for, a config path relative to cwd, `print` instead of a
logger, the volume of tests.

## 4. Upgrade and layers: corrections to the plan

The plan (sections 3–4 of `docs/v0.4-plan.md`) is right in substance: version,
migrations, `--dry-run`, backup, the core / profile / defaults / local layers. Three
places need refining.

**Merging the user's edits.** In the plan, user lines that are not in the old template
move to `## Overrides`. That loses context: an edit inside a rule turns into a separate
duplicate line. The copier scheme is better:

1. On every install, the rendered block is saved to `~/.lab-forge/base/<file>.md`.
2. On upgrade, if the sha of the block on disk matches the sha in the marker, the block
   is simply replaced.
3. Otherwise `git merge-file <on disk> <base> <new render>` runs. Without conflicts the
   result is written; on a conflict a `.rej` is put next to the file, the file is not
   changed, and `--dry-run` shows both versions.
4. For v0.3 blocks the base is rebuilt exactly: the template from
   `git show 8417b6c:.../global-agents.md` and the canary from `state.md`. The migration
   puts these templates into `scripts/migrations/`, so git history is not needed.
5. For v0.1/v0.2 there is no base: the agent wrote the files from a template, they are
   not a render. The plan's method works here, but by sections, not by lines:
   - sections with v0.1 template headings ("Size the task first", "How code is written
     here", "Check before saying "done"", "Delivery") are replaced by the core;
   - "Read first", "Invariants", "Languages", the `{{pain_point_rule}}` item and
     everything unrecognised stay as facts outside the block;
   - the text pointer is replaced with `@AGENTS.md`.

**Detecting the version.** Fingerprints from the actual files:

| Version | Sign |
|---|---|
| v0.1 | repo `.lab-forge/state.md` without a `- Mode:` line, rules heading `# Rules for AI agents -`, no `~/.lab-forge/` |
| v0.2 | the same, but `state.md` has `- Mode:` |
| v0.3 | `~/.lab-forge/state.md` with `- Canary:`, marker `lab-forge:begin sha=` without `v=` |
| v0.4 | marker `lab-forge:begin core v=0.4.0 sha=…`, `- Version:` in both `state.md` |

One more hole the plan does not cover: `install_global.py:200-201` silently overwrites
`~/.lab-forge/AGENTS.md`. In v0.4 this file also goes through base + merge.

**Core.** Claude Code does not honour a priority order written in prose ("Claude may
follow either one"). So the core rests on three mechanisms, not on the order of lines:

1. `guard.py hook` blocks edits of the `core` and `profile` blocks and of the file
   `~/.lab-forge/core.md`.
2. `tune.py add` refuses a line that weakens a C rule (the list of negation phrases
   lives in `core.md`).
3. `install_global.py check` compares the sha of the core.

We keep a single ordering line: "Core rules always hold; profile and local rules may
add or tighten, never relax them."

## 5. Bench: corrections

The plan (section 5) already introduces `methodology` and `tests` with weight ×2,
mutants, 3 repeats and headless runs, and sets the rule: the bench is only extended,
old metrics and results do not change. Everything below is new columns and rows on
top. I add:

- **A cheap objective test check without hand-written mutants: "tests bite".** The
  tests added in a step run against the code from before that step (the previous
  step's snapshot plus the new tests). At least one must fail. It works on all 4 cases
  without writing patches. Hand-written mutants stay only for churn and rparse, where
  methodology matters.
- **Bare `pytest` as a metric**, not only as an item for the judge.
- **Tokens:** the 4 usage fields, `cost_usd`, weighted tokens (section 2, item 1). The
  old sum stays as a column; the epic target "no worse than bare" is additionally
  counted by `cost_usd` per solved task.
- **The judge is Fable 5.1 (Yeldos's decision, 2026-10-19).** Agents run on Opus 5.5,
  the judge on `--judge-model claude-fable-5-1`. The flag already exists
  (`bench.py:627`); it only needs the same Claude key, no separate paid API. Fable is a
  different line but the same vendor, so self-preference shrinks rather than vanishes.
  We compensate: X/Y in both orders, a disagreement counts as a tie; replies do not
  quote `AGENTS.md` (otherwise the arm is visible). `--judge-cmd` with `codex exec` /
  `gemini -p` is postponed.
- **Auth for headless.** This task's runtime has neither `ANTHROPIC_API_KEY` nor
  `CLAUDE_CODE_OAUTH_TOKEN`, so no headless measurement was made. Stage 3 needs the key
  in the bench environment.

## 6. Stage 2 tasks

Four tasks. 1 and 3 can run in parallel, 2 depends on 1 (core and templates), 4 goes
last.

Files: `assets/templates/global-agents.md` (split into `core.md` and `defaults.md`),

`references/profiles/classic-ml.md`, `references/profiles/llm-agents.md`,

Acceptance: core ≤ 30 lines, core + repo template ≤ 60 lines (checked in
`verify_setup.py`); the profile reaches the repo verbatim, seed included;
`smoke.py` is green; the rules diff is shown in the PR.

**2. Upgrade from v0.1/v0.2/v0.3.**
Files: a new `scripts/upgrade.py` and `scripts/migrations/` (v0.1–v0.3 templates),
`scripts/install_global.py` (version, base, merge, no silent overwrite,
`uninstall`), `SKILL.md` (Upgrade mode), `tests/test_upgrade.py` with fixtures.

gives an empty diff; no duplicate blocks, hooks or skills; an edit inside a v0.3 block
merges without loss, a conflict produces `.rej` and leaves the file unchanged;
`--dry-run` writes nothing to disk; a backup is made before writing.

**3. Core protection.**
Files: `scripts/guard.py` (`core`/`profile` blocks), `scripts/tune.py` (refusal for
weakening C rules, `replaces D<n>`, no `CLAUDE.local.md`), `tests/test_layers.py`.
Acceptance: an Edit inside the core block is blocked by the hook; `tune.py add "commit
straight to main"` is refused with a clear message; an override for a D rule is applied
and rolled back through `undo`.

**4. Bench v0.4.**
Files: `bench/rubric.md`, `bench/report.py`, `bench/bench.py`,
`bench/cases/{churn,rparse}/case.toml`, `bench/test_bench.py`.
What: `methodology` and `tests` ×2 (weight from the plan), "tests bite", hand-written
mutants for churn and rparse, bare `pytest`, the 4 usage fields and `cost_usd`, Fable 5.1
as the default judge (`--judge-model claude-fable-5-1`), X/Y in both orders, `--reps 3`

fields empty); on the v0.3/bare churn snapshots the "tests bite" metric tells the v0.3
config test apart from the bare test.

Stage 3 of the epic: a headless A/B of v0.4 against v0.3 and bare, 3 repeats, then
`upgrade --dry-run` on Yeldos's v0.1 install, and `--apply` only after Yeldos says "yes".
